# Loopora Contracts

These contracts sit below `HUMAN-SHAPED-LOOP.zh-CN.md` and `README.zh-CN.md`. They define what must stay true while the
implementation stays free to shrink.

| Boundary | Stable claim | Primary code | Verification | Not a contract |
| --- | --- | --- | --- | --- |
| Product shape | Loopora preserves task-scoped human judgment across long Agent work. The Loop, not a prompt pack or DAG engine, is the primary object. | `src/loopora/service*.py`, `src/loopora/workflows.py` | README checks, shared compiler/runtime contracts, verdict tests | Role count, exact copy, visual layout |
| Dual entry | Web composer and Agent Native are peer entry surfaces into the same Core. Web is full-function; Agent Native must not grow a second compiler. Agent-returned Web URLs and generated fallback/recovery/submit CLI commands must observe the same Loopora home as the Agent command that created the preview or run. | `service_alignment.py`, `service_agent_adapters.py`, `bundles.py`, `agent_web.py`, `agent_adapters.py`, `service_agent_native.py` | Web READY/run smoke, Agent `/loopora-plan -> /loopora-run`, shared bad-bundle error, Agent Web home identity check, generated command home-preservation test | Web-only observer framing, adapter-specific prose |
| Compiler | The compiler turns task judgment into a reviewable and runnable Loop. Web dialogue, Agent candidate plans, YAML import/export, preview, and run creation all use the same bundle normalization and semantic lint. READY preview must reflect current canonical content. | `src/loopora/bundles.py`, `service_bundle_assets.py`, `service_alignment.py` | One shared success path and one shared failure path across Web/Agent | UI summaries, traceability aliases, stale validation |
| Context choice | Web and Agent Native use the same workdir context resolver before continuing, improving, or starting fresh. Exact Agent binding may resume automatically; ambiguous or cross-session recovery must surface choices instead of guessing, and Agent recovery choices must include status/hint text plus enough status/timestamp metadata to distinguish similar labels. Status/hint text explains whether the choice resumes active work, starts a READY preview, replays a passed terminal run without new Agent work, continues evidence from an unproven terminal run, still needs review, or needs candidate repair. Terminal run choices expose linked run status plus task verdict status/summary so passed replay and next-evidence continuation are not ambiguous. Runnable choices expose copyable slash and CLI run commands; non-runnable choices withhold run commands and instead expose preview/repair evidence such as `preview_url`, `preview_path`, `validation_error`, `repair_focus`, `next_plan_command`, and plan-file paths when available. | `service_alignment.py`, `service_agent_adapters.py`, Web alignment context route | workdir context resolution tests, Agent no-binding recovery tests, terminal recovery verdict tests, recoverable-context command/hint tests | Choosing the newest run by default, silent fresh/reuse switches |
| Bundle | Bundle is a Web-operable exchange file: generate, edit, preview, import, export, replace, delete. It is not a long-term catalog or governance object. UI projections such as summaries, traceability aliases, or diagnostics are derived views. Record deletion and local artifact cleanup are separate; non-critical cleanup failure must be visible as a warning. | `bundles.py`, bundle routes/templates | YAML import/export, preview, run handoff, cleanup warning tests, absence of lineage/governance-card defaults | Lineage, revision identity, cards, dashboard metrics |
| Runtime | Run status and Loop verdict are separate. Evidence refs, coverage, and GateKeeper verdict decide whether the task is proven. Ledger entries keep related evidence refs citable without duplicating the same ref inside one entry, role handoffs keep blocking items unique so downstream users see issue count rather than duplicate derivation paths, a later positive coverage claim without supporting evidence must not promote an already blocked target to Proven, and a later supporting coverage proof replaces historical blocked refs in Proven target evidence refs. Self-healing transient database retries remain in `service.log` diagnostics but do not appear in the default terminal warning stream. | `service_run_*`, `service_agent_native.py`, `context_flow.py`, `run_takeaways.py`, `db.py` | verdict/status tests, evidence ledger checks, related evidence ref dedupe check, handoff blocker dedupe check, coverage supporting-ref replacement test, database retry diagnostic test, run detail smoke | Process success as task proof, full artifact shape, transient retry log as user action |
| Workflow | The default user model is linear and explainable: `Builder -> optional Inspector/Guide -> GateKeeper`. Advanced parallel/control fields are compatibility or expert-only surfaces. | `workflows.py`, workflow runtime | default preset tests, minimal advanced negative/compat checks | Parallel/control as default fixture or journey path |
| Agent Native | Agent Native lets the current Coding Agent remain the execution subject while Loopora owns planning/review, run-stage recovery, host-native role dispatch, evidence handoffs, submit acceptance, and task-proof/lifecycle separation. `/loopora-plan` is the planning stage for creating, revising, repairing, or tightening reviewed Loop previews; `/loopora-run` is the run stage for starting, resuming, replaying, or continuing evidence under that reviewed Loop. Project entries stay thin Loopora-managed dispatchers, and compact JSON/plain summaries must surface actionable recovery, dispatch, evidence, and verdict state before agents rely on full payloads. Field-level projections for current-step, submit repair, blocked-action, and evidence-handoff surfaces are owned by the narrower rows below plus contract tests, not by this umbrella row. Templates/tests inherit host model/provider defaults unless explicitly supplied. | `agent_adapters.py`, `service_agent_native.py`, `service_agent_native_contracts.py`, `cli_agent_adapter_commands.py`, `cli_agent_native.py`, `cli_agent_step_presenters.py`, `cli_agent_submit_repair.py` | adapter entry validator, capsule/submit contract, run/next/submit summary tests, recovery-token tests, generated command home-preservation test, no hardcoded model/effort, opt-in real-agent probe | Nested provider CLI execution, status-only slash commands, exact prose or complete JSON shape |
| Agent Native current-step recovery | When `loopora agent <adapter> next` cannot resolve the current host context binding but the workdir contains recoverable Loopora contexts, it must return structured recovery instead of a raw conflict. JSON starts with `agent_next_recovery_summary`; active-run choices expose a direct `next_agent_command` using the linked run id, while READY preview choices still route through `/loopora-run` or its CLI equivalent. | `cli_agent_native.py`, `service_agent_adapters.py` | agent-next no-binding recovery test, recoverable-context command/hint tests | Guessing the newest run, silently rebinding the host context |
| Agent Native submit repair | Recoverable submit failures must explain both sides of the mismatch before asking the Agent to edit JSON. Plain and JSON repair output expose the active result template, active filled-result path when known, result outbox when known, exact known ids, compact active known-evidence classifications, and active coverage target ids so the Agent can copy the template, save the filled copy to the right file, cite only valid evidence, and avoid inventing target IDs. JSON starts with `agent_submit_repair_summary`, includes the submitted file's `loopora_host_dispatch` summary when present, and points stale-step recovery to the active template, active filled-result path, active step, exact known ids, compact active known-evidence classifications, and the current schema lookup command while preserving an explicit workdir when one was used. | `cli_agent_submit_repair.py`, `service_agent_native.py`, `service_agent_native_contracts.py` | host-dispatch submit repair tests, stale-step and unknown-evidence submit repair tests, unfilled result template repair tests | Raw conflict-only errors, guessing stale step identity from filenames |
| Agent Native blocked actions | Blocked submit and iteration-repair summaries must not surface placeholder or contradictory next actions such as `None` or `No action needed`. When GateKeeper evidence-gate blockers or contract target IDs are present, compact JSON and plain output derive a concrete repair action or point users to `required_coverage` / `top_coverage_gaps` instead of surfacing bare codes. | `cli_agent_step_presenters.py`, `service_agent_native_contracts.py`, `service_agent_native.py` | submitted blocking item tests, iteration repair focus tests, contract-target blocker explanation test | Trusting blocked role-provided next action text over blocker semantics |
| Agent Native evidence handoff | Current-step summaries must show not only citable evidence IDs but also bounded latest evidence IDs, bounded evidence-ref summaries with role/result, GateKeeper support classification, support reason, claim, coverage target IDs, compact proof/artifact paths, top coverage gaps when present, and a coverage-classification note when citable evidence exists before any coverage target has been classified or when newly citable supporting evidence has not yet been reclassified after older weak/blocked coverage. That note must disappear once the only remaining gap is `gatekeeper.finish`, because the next GateKeeper verdict is the expected closure path rather than an unclassified Builder-evidence problem. Successful submit summaries show the submitted role's own coverage classifications and counts before the next-step handoff, so the user can see what the just-finished role changed without opening ledger artifacts, and coverage aggregation preserves explicit missing classifications as missing gaps rather than blockers. When a blocked GateKeeper opens a new iteration, compact JSON/plain output and the result template's `loopora_result_contract` must also expose `iteration_repair` source, blocking items, evidence refs, top gaps, and the recommended next action, while blocked coverage gaps retain the blocker evidence ref as well as cited upstream refs and reconcile target-specific blockers against current top gaps so resolved prior blockers do not remain as active instructions. The compact handoff must make blocked or non-supporting evidence visible before a role opens the full capsule/template, without embedding the full ledger, making the citable ID window disagree with evidence refs, or implying that unclassified Builder evidence is already target coverage. | `cli_agent_step_presenters.py`, `cli_agent_submit_repair.py`, `service_agent_native_contracts.py`, `service_agent_native.py`, `context_flow.py`, `evidence_coverage.py` | submitted coverage summary test, explicit-missing coverage result test, blocked-target blocker-ref test, unclassified-new-evidence coverage note test, gatekeeper-only gap note suppression test, agent-next known-evidence-ref summary test, current-step known-evidence plain output test, GateKeeper support classification tests, iteration-repair summary tests, result-template iteration-repair test | Full ledger dump, using support labels as final verdicts |
| Adapter compatibility | Loopora only owns `.loopora/` state plus host entry files carrying `LOOPORA-MANAGED` markers or manifest hashes. Project instructions, global config, model/provider defaults, MCP servers, permissions, and unrelated hooks remain host/user/plugin owned. Public adapter names stay `loopora-*`; removed managed entries are deleted only when ownership is provable. Install and successful check results expose the same next-step slash-command handoff, a copyable first task message example that names goal, fake-done risks, required evidence, and judgment tradeoffs, copyable diagnostic check commands in human and JSON modes, and a host-specific visibility hint for missing `/loopora-plan` or `/loopora-run` entries. Adapter checks distinguish "not installed yet" from damaged installed entries so missing managed files before install are explained as expected setup state, while installed drift exposes failed file-level checks with role-agent repair context when native dispatch config is missing. Install conflicts on user-owned entry files fail closed without overwriting and keep `--json` output structured with conflicting paths and recovery commands. `loopora agent <adapter> check` is a friendly alias for the same static entry check, so users who look under the Agent runtime namespace still get actionable install state instead of a generic missing-command error. | `agent_adapters.py`, CLI init/uninstall | non-managed conflict tests, managed obsolete cleanup, namespaced-entry/no-model-default tests, install JSON next-step test, pre-install check recovery tests, missing role-agent config check, agent-check alias test | Overwriting host config, generic command/tool names, unowned uninstall cleanup |
| Web Composer | Web supports conversation, compile, READY review, edit/improve, YAML import/export, create run, and run/evidence/verdict observation. | Web routes/templates/static pages | route availability, READY preview, create-run, run detail journey | CSS, DOM hierarchy, static wording, pixel layout |
