# Loopora Service Boundaries

This document carries implementation ownership boundaries that would otherwise drown the product-facing contracts. It is still stable design evidence: update it when modules move, split, merge, or change ownership. Product behavior, public contracts, and user-path claims stay in `contracts.md`.

## Service Boundary Inventory

### Service Composition

- `LooporaService` remains the only compatibility pass-through facade.
- `LooporaAppServices` exposes explicit component methods through `AgentNativeService`, `RunService`, `ProjectionService`, `AlignmentService`, `BundleService`, and `AssetRegistryService`.
- Component services must not expose runtime-wide `__getattr__` pass-throughs or cross-boundary methods; routes and callers should choose the component that owns the stable behavior.
- `LooporaServiceRuntime` remains a service-app compatibility runtime for facade state sharing, not another component boundary. Normal construction applies startup recovery/backfill; passive status construction explicitly skips those writes and may reconcile only through the scoped status action.
- `service.py` owns service creation and local App-state-open error projection across logging, settings, repository initialization, and runtime assembly. Normal construction initializes writable App state; passive status construction uses non-creating App paths, read-only settings and Repository modes, and no file-log setup.
- `db.py` owns SQLite connection retry diagnostics and keeps final writable connection failures as log-file evidence rather than terminal-facing product errors. Read-only Repository construction validates a compatible existing schema without initializing or stamping it, opens SQLite in read-only/query-only mode, and rejects write transactions.
- Service-to-service private helper imports are retired, not a pattern to copy; new service-to-service private helper imports must fail architecture tests unless this section is updated with a deliberate extraction plan.
- `dev_check_default_fast.py` owns the default-fast command catalog; `dev_check_guide_types.py` owns focused-guide DTO shape; focused-check guide catalogs live in `dev_check_guide_first_use.py`, `dev_check_guide_web.py`, `dev_check_guide_agent_native.py`, `dev_check_guide_alignment.py`, `dev_check_guide_core_execution.py`, `dev_check_guide_runtime.py`, and `dev_check_guide_open_source.py`; `dev_check_guides.py` is only the compatibility aggregate.
- `dev_check_changed_files.py` owns Git/provided changed-file projection and rename collapse; `dev_check_focus.py` owns focused-guide selection, path matching, and matched/unmatched guide projection.
- `dev_check_package.py` owns the package-build step facade and verification aggregation; `dev_check_package_lifecycle.py` owns package-build serialization and generated-artifact cleanup; `dev_check_package_contents.py` owns wheel/sdist runtime/public-content checks; `dev_check_package_metadata.py` owns public package metadata and install-entry checks; `dev_check_package_provenance.py` validates path-free wheel/sdist source identity; `dev_check_package_policy.py` owns package distribution constants. `package_source_provenance.py` is the shared build/runtime source-revision boundary.
- `dev_check_types.py` owns shared dev-check DTOs; `dev_check_execution.py` owns default/focused step execution, subprocess invocation, static-JS checks, and progress event projection.
- `dev_check_report.py` owns dev-check report payload assembly and next-action readiness projection.
- `dev_check_focused_evidence_actions.py` owns focused evidence coverage and final/remaining PR-evidence action projection; `dev_check_next_actions.py` owns next-action readiness and profile-level action selection; `dev_check.py` owns the public default/focused orchestration entry.
- `dev_check_command_projection.py` owns copyable dev-check command construction for next actions, recovery, release-plan evidence, and PR evidence source projection; dev-check presenters should not reconstruct current-entry, changed-file, focused, focused-ran, or workdir flags locally.
- CLI dev presentation modules own user-facing dev command evidence: `cli_dev_check_output.py` owns plain dev-check result/progress output, focused recommendation readability, ignored/unmatched changed-file display, and PR-evidence decision hints; `cli_dev_check_recovery.py` owns recoverable dev-check errors plus copyable command normalization for current CLI entries, workdirs, and changed-file scope; `cli_dev_next_action_text.py` owns shared dev-check next-action text, guide suffixes, and changed-file list summaries; `cli_dev_pr_evidence.py` owns copyable PR evidence payload/printing; `cli_dev_release_plan.py` owns maintainer release-readiness planning payloads, blockers, release evidence actions, and plain release-plan output; `cli_dev_reset_output.py` owns dev reset JSON/plain recovery output, scope descriptions, destructive apply commands, and readiness next-action projection.
- `recovery_archive.py` owns private archive scope, consistent SQLite backup, managed-file collection, format validation, checksums, and archive privacy metadata without opening the Service or migrating App state; `recovery_restore.py` owns exact-source identity, byte comparison for ordinary files, logical SQLite-snapshot comparison for the App database, no-overwrite planning, and missing-file restoration; `cli_recovery_projection.py` owns versioned CLI summaries, purpose choices, restore states, and next-action readiness; `cli_recovery_language.py` owns command language continuity; `cli_recovery_commands.py` owns create/inspect/restore presentation.

### Runner And Run Execution

- Shared runner runtime context objects, runner step selection plans, and runner step-claim request assembly live in `engine.runner_context` and `engine.runner_runtime`; Agent Native must not import `service_workflow_execution` private types.
- Runner execution owns `execute_run`; the old generator/tester/verifier legacy runtime is removed, and a run with no strategy snapshot fails closed instead of dispatching a second runtime.
- Executor loop state, bundle-candidate outcome classification, bundle executor-settings issue selection, executor session transition planning, executor request construction, native resume fallback request mutation and event payload, executor session-ref merge/event payload, and executor output action classification live in `service_alignment_execution.py`.
