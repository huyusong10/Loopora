# Loopora Run Contract

## Purpose

Start, resume, or continue evidence collection for the reviewed Loop preview bound to this Agent session or workdir.

## Run Command

`LOOPORA_AGENT_ENTRY_SOURCE={{marker_source}} {{loopora_cli_entry}} agent {{adapter}} run --workdir "$PWD"{{context_bits}} --entry-source {{marker_source}} --json --compact-json`

## Recovery

If the command returns `ready: false` or `loop_recovery`, report that recovery path and stop before role dispatch.

## Work Panel Use

Read the top-level JSON `summary.agent_work_panel` first. In the main Agent session, report `agent_work_panel:` before technical paths after `/loopora-run`, `loopora agent ... next`, and submit; include `state`, `current_role`, `target_agent`, `role_handoff_status`, `next_action`, `evidence_focus`, and `top_gaps` so the user sees who acts next, whether host dispatch has started, and which evidence gap drives the step. Bash/tool/JSON output alone does not count as the main-session work panel.

## Role Dispatch

Invoke the exact host-native role agent named by `next_step.role_dispatch.target_agent`; copy `summary.next_role_dispatch_message` verbatim when present, and never submit inline work as if a role agent ran.

## Result Template

In the main Agent session, open the active result template, preserve `loopora_host_dispatch`, fill only `result`, and submit the filled copy with the provided command.

## Proof Boundary

Loopora proof comes only from submitted evidence refs, coverage, and task verdict; todo, host status, and native trace are experience projections.

## Failure Modes

If dispatch, schema, stale-step, or proof validation blocks submit, report the complete typed repair envelope and stop before inline fallback or shell-filtered summaries.

## Detailed Contract

Enter Loopora's run stage. Start, resume, or continue evidence collection for the reviewed Loop preview associated with this session or workdir.

Use this entry when the user says to run, resume, continue, keep going, close evidence gaps, or perform the next proof pass for the current Loop. If the user asks to change the judgment structure, evidence requirements, GateKeeper strictness, role responsibilities, workflow shape, or plan repair direction, stop and tell them to use `/loopora-plan` or Web review first. Do not silently rewrite the Loop from `/loopora-run`.
In Claude Code non-interactive sessions, a failed `Skill` tool invocation with `disable-model-invocation` is an entry-visibility signal, not permission to simulate `/loopora-run` through a generic `Agent` or `Task` call. Stay in the main Agent session, read the project-local managed references if needed, and run the explicit `{{loopora_cli_entry}} agent {{adapter}} run` Bash command with the same entry source; use host-native role `Agent` / `Task` dispatch only after Loopora Core returns a role `next_step`. Do not inspect `$HOME/.claude`, global skill directories, Loopora manifests, binary/PATH probes such as `which loopora`, `command -v loopora`, `type loopora`, `echo $PATH`, `loopora --version`, `loopora --help`, `loopora init claude`, `loopora agent claude check`, parent directories, or broad project/file discovery to verify the entry; the project-local managed entries and references are the contract, and the explicit run command is the capability check. Do not run the combined preflight `which loopora && loopora --version`, directory-listing preflights such as `ls`, or any PATH/help/init/check probe before `/loopora-run`; after reading the managed references, the next Loopora Bash action should be the primary run/next/submit command returned by Loopora.

   - `loop_recovery=plan_first` means this Agent session/workdir has no ready Loop preview or recoverable run context. If the answer is only a rough goal or still lacks Loopora fit reason, fake-done risk, evidence, or judgment tradeoff signal, return Web review prefill or ask one main-session follow-up rather than synthesizing a READY candidate. Do not create a plan implicitly from `/loopora-run`.
   - `loop_recovery=active_run_conflict` means another active Loopora run already owns this workdir. Report the active run id/status/current step, `active_run_url`, `active_run_url_status`, and `active_run_url_web_start_command` when present, continue it with `next_active_run_command`, or ask before stopping it; do not start a second run in the same workdir.
   - `loop_recovery=finish_web_review` means the current `/loopora-plan` result needs Web review or a not-fit user decision before `/loopora-run`; report `preview_url`, `preview_url_status`, `preview_url_web_start_command`, `requires_web_alignment`, `loopora_fit_contradiction`, `review_status`, `review_focus`, `review_recommended_action`, `review_reply_preview`, and `next_review_step` when present.    - `loop_recovery=repair_candidate_plan_file` means the candidate plan file failed validation; report `agent_work_panel`, `repair_action`, `preview_url`, `preview_url_status`, `preview_url_web_start_command`, `requires_candidate_repair`, `loopora_fit_contradiction`, `repair_task_message`, the source plan / preview copy paths from the context card or session, and the validation / repair focus when present. Treat `agent_work_panel.next_action` / `repair_action` as the first-screen instruction. Do not inspect alignment session artifacts, manifests, generated preview copies, Loopora source/help output, or filesystem-wide discovery as the repair path.

   - `loop_recovery=preview_not_ready` means the associated preview is not ready; return to `/loopora-plan` or Web review.
   - `loop_recovery=repair_context_card` means the local context card is unreadable or invalid. Run `{{loopora_cli_entry}} init {{adapter}} --check --workdir "$PWD"` to diagnose, then either repair the file or use `/loopora-plan fresh` if the user wants a new Loop.

Do this in your own user-visible reply; do not assume Bash/tool/JSON stdout is visible enough. ## Boundaries

- If the command says no Loop preview is associated with this session/workdir, tell the user to run `/loopora-plan` first.
- If the command returns `loop_recovery`, report that recovery path and stop; do not proceed to role dispatch.
- Do not create a bundle implicitly from `/loopora-run`.
- Do not bypass Loopora's bundle import, run lifecycle, evidence ledger, or GateKeeper verdict.
- Do not launch `codex`, `claude`, or `opencode` from inside this entry. The current host Agent must dispatch to the named host-native Loopora role agent and submit wrapper JSON to Loopora.
- Do not treat host auto-activation, compatibility-layer routing, or injected rules as proof that the required Loopora role agent ran.
- Do not copy credentials, API keys, tokens, or environment secrets into Loopora result files or evidence notes.
